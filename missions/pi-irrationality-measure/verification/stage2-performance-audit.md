# Stage 2 extraction performance audit

Scope: read-only inspection of the Stage 2 oracle/runner, `preflight_logged.py`, and the installed Lean 4.33.1 `Frontend`, `Import`, `Environment`, `ImportingFlag`, `Language.Lean`, and `Server.FileWorker` implementations. No Lean process was started and no oracle, runner, pins, or source files were changed.

## Findings from source

- The current oracle intentionally handles one source path per invocation: `PiExponentMetadata.main` reads `args[0]`, reads that file's bytes, builds a `Parser.InputContext`, calls `Parser.parseHeader`, `processHeader`, and `IO.processCommands`, then derives facts from that file's commands/info trees. It explicitly describes itself as re-elaborating “the one file” with InfoTree recording enabled (`verification/TargetAxioms/SketchOracle.lean:21,125-141`). The wrapper only delegates the argument list (`verification/RunSketchOracle.lean:1-4`). This is why Stage 2 receives source-specific syntax, references, and byte-mapped positions.
- `preflight_logged.py` invokes a fresh child process for each source using `subprocess.Popen`; in sketch mode it passes one source path after `--run RunSketchOracle.lean`. The allowed timeout is at most 300 seconds and the timer covers the child-process lifetime. It pins `LEAN_NUM_THREADS=1` (`scripts/preflight_logged.py:29,51,70-84,83-100`). Therefore process startup, loading the runner/oracle, header imports, target elaboration, and JSON emission all consume the file's budget.
- Lean's `IO.processCommandsIncrementally` accepts a prior `IncrementalState` expressly for reuse “done with the same state (but usually different input context)” (`Lean/Elab/Frontend.lean:99-127`). This is edit reuse within a document's command-snapshot chain, not a batch API for unrelated modules. `IO.processCommands` passes `none` for that prior state (`Frontend.lean:129-131`).
- The normal header path is per file: `Language.Lean.process` parses each file's header and calls `Elab.processHeaderCore`, which imports the header imports and creates a header environment (`Lean/Language/Lean.lean:388-... and 488-522; Lean/Elab/Import.lean:138-180`). The public `Environment.importModules` call enters `importModulesCore ... |>.run` for that import set (`Lean/Environment.lean:2438-2449`). `importModulesCore` keeps a `moduleNameMap` in its import-state and avoids re-reading a module if it has already been seen in that import-state (`Environment.lean:2203-2228`); the inspected code does not expose a process-global imported-module cache reused by a later independent `importModules` call.
- `withImporting` is not a module cache. Its documented role is to set/reset a global flag allowing initializer code to update global references; it also disables initializer execution on exit (`Lean/ImportingFlag.lean:39-58`).
- The Lean 4.33.1 file server is explicitly single-file-per-worker for imports. `setupImports` says imports can be loaded at most once per process because they cannot be unloaded; a second import setup requests a watchdog restart (`Lean/Server/FileWorker.lean:367-390`). It uses `Language.Lean.process` plus an incremental processor for the one document (`FileWorker.lean:449-466`). This is strong evidence that the stock server is not a supported way to process hundreds of independent files in one worker while reusing imports.
- Lean supports saved incremental snapshots, but `Frontend.loadIncrSnapshot` reconstructs imports from recorded module artifacts and reinitializes imported initializers; the source calls this a central incremental “HACK” and notes theoretical behavioral divergence for unusual initializers (`Lean/Elab/Frontend.lean:197-... and 315-334`). It is designed to resume a file snapshot, not to multiplex arbitrary files. Its separate `LEAN_IMPORT_WORKERS` comment concerns parallel loading of compacted regions while loading such a snapshot, not a general cross-file module cache.

## Assessment

The exact proposal “one Lean process, arbitrary independent files, unchanged Stage 2 facts, 300-second budget per file, and no repeated import work” is **not supported by the inspected stock interfaces**. The CLI path starts a fresh process per file; `processCommandsIncrementally` only reuses one file's snapshots; and FileWorker deliberately restarts rather than loading another file's imports in the same process.

A custom Lean driver could in principle loop over multiple input paths and, for each path, create a fresh `InputContext`, parse the original header, establish the proper module/import environment, create a fresh command state with InfoTree enabled, elaborate the original bytes, and emit that file's records before proceeding. That preserves the shape of the oracle's current work in principle, but merely looping `IO.processCommands` does **not** avoid imports: it accepts an already-created environment and does not parse/import the next file's header. Reusing a common imported environment would require carefully proving that each file has the same effective imports/options/plugins/module setup, rebuilding a clean per-file command state and main-module identity, and matching initializer/environment-extension behavior. The inspected Lean sources do not provide an official `withImporting` or Frontend batch API that does this safely. Such a driver is a separate implementation that needs byte-for-byte record parity, source-position parity, declaration/type checks, timeout/cancellation tests, and `#print axioms` parity before it can replace the current method.

Per-file deadlines are feasible in principle in a custom sequential driver by measuring each file's elapsed time and stopping that file at 300 seconds, but a timer alone is insufficient: Lean elaboration is asynchronous, and cancellation must ensure no stale task mutates or contaminates the next file's state. The server's cancellation/task model is per-file snapshots, not a documented batch-worker cancellation contract. There is no source evidence that a custom multi-file process can meet the current deadline and output invariants without testing.

## Recommendation

For the ongoing extraction, do not switch to a custom multi-file process mid-run. Keep each file's Stage 2 authority tied to a fresh file environment and preserve the current 300-second child-process boundary. To reduce overhead safely, first use the existing captured Lean runtime path (when its hashes validate) so `preflight_logged.py` can invoke the Lean executable directly instead of starting `lake env` for every file; this removes Lake startup only, not Lean process startup/import loading. Any larger gain from shared in-memory imports requires a separately reviewed driver and a parity campaign over representative files before the full extraction is resumed with it.

The expected improvement from direct executable invocation is limited: Lean process initialization and imported `.olean` loading still occur for every file. OS filesystem caching may reduce physical disk reads after warm-up, but it does not establish reuse of decoded module environments and is an inference, not a guarantee from these sources.
